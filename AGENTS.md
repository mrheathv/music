# Making game music in this repo: guide for agents

This repo holds the soundtrack for Contraflow Games' city builders, and the method used to
make it. Every track is **generated by a Python script**: synthesizers, drums and effects are
built from oscillators, filters and noise. There are no samples and no third-party audio, so
everything is original and free to ship.

Read this whole file before making a track. It records what worked, what failed, and the
checks that stand in for listening (you cannot hear the output; the person you work for can).

## Quick start

```bash
pip install -r requirements.txt          # numpy, scipy, soundfile; ffmpeg with libvorbis must be on PATH
python3 necity/scripts/neon_grid.py      # renders build/neon_grid_raw.wav and prints a seam check
python3 tools/finalize.py build/neon_grid_raw.wav necity/tracks/neon_grid.ogg
bash tools/build_all.sh                  # re-renders every track (about 90 s)
```

Renders are deterministic (each script uses a fixed random seed), so `build_all.sh`
reproduces the committed audio exactly: the WAV masters in `build/` are bit-identical. The OGG
*files* still differ byte for byte after every encode, because Ogg gives each stream a random
serial number, so git will show re-encoded OGGs as modified. Only commit an OGG whose track
you actually changed, and restore the others with `git checkout -- '*.ogg'`.

## House audio spec (every track must meet this)

- **Format:** OGG Vorbis q6, 44.1 kHz stereo, in `<game>/tracks/`.
- **Loudness:** -18 LUFS integrated, true peak no higher than -1 dBTP (current tracks peak
  between -5 and -8 dBFS). `finalize.py` enforces this, which leaves room for game sound effects.
- **Seamless loop at the file boundary:** the engine loops the whole file with no fades or
  padding. The OGG must have exactly the raw render's sample count; `finalize.py` checks this.
- **Length:** a whole number of bars. The standard is 24 bars in three 8-bar sections, about
  1 minute:
  1. groove: no melody, lighter drums
  2. melody enters, full drums
  3. melody variation, extra lift

  The last bar leads back into bar 1 (a tom fill, a dropped beat, or a chord that resolves to
  the first chord).

## How a track script is built

Each script follows the same order. Keep it so the scripts stay easy to compare.

1. **Constants:** `SR`, `BPM`, `BARS`, `LOOP`, `N` (loop length in samples), the seed.
2. **DSP helpers:** `lp`/`hp`/`bp` (Butterworth), `add(buf, sig, t, pan)`, band-limited
   `saw`/`pulse` (PolyBLEP; never use naive saws, they alias), `adsr`.
3. **Instruments:** each is a function that returns a note as a numpy array.
4. **Composition as data:** a chord table (bass MIDI note, pad voicing, arpeggio notes), an
   8-bar `PROG`, and melody phrases as lists of `(16th step, midi, length in 16ths)`.
5. **Arrangement loop:** for each bar, look up the section (`bar // 8`) and add notes to stem
   buffers (`pad`, `bas`, `arp`, `ld`, `drm`, ...). Record kick times.
6. **`loopify` each stem, then effects:** sidechain, ping-pong delay, reverb, saturation.
7. **Seam check, then write** `build/<name>_raw.wav` (24-bit).

## Seamless-loop rules (critical)

These produced exact seams, with a difference of about 1e-13. Break any one and the loop clicks.

1. **Render events once** into a buffer of length `N + tail`. An event at negative time
   (from timing jitter) wraps to `t + LOOP`; `add()` already does this.
2. **Fold the tail:** `y[:len(x) - N] += x[N:]`, so reverb and release from the last bar land
   at the start.
3. **Tile twice before any effect** (`np.concatenate([y, y])`), run all filters, delays and
   reverbs on the doubled buffer, then **keep the second copy** (`mix[N:]`). The filters then
   start already "warmed up" by the end of the loop.
4. **Anything driven by time must repeat exactly per loop.** LFOs and tape wobble need a whole
   number of cycles per `LOOP`, for example `rate = round(0.35 * LOOP) / LOOP`.
5. **Place time-indexed effects by integer sample index modulo `N`,** never by
   `int((t + LOOP) * SR)`. A real bug: sidechain ducking computed from float times landed one
   sample apart in the two copies, and the seam was off by 0.45. Use the `kick_idx` pattern
   in the existing scripts.
6. **Nothing random after `loopify` may differ between the two copies.** A random reverb
   impulse response is fine, because it is applied to the whole buffer.
7. **Every script must print the seam check**
   (`max |mix[N-4000:N] - mix[2N-4000:2N]|`). Anything above about 1e-9 is a bug: find the
   stage at fault by checking each stem and effect separately.

## What works and what doesn't (important)

**Works: genres whose real instruments are synthesizers.**
- Synthwave: detuned supersaw pads, saw/pulse bass with a filter pluck, pulse arpeggios,
  80s drum machine with a gated-reverb snare.
- Ambient electronica / "systems music": FM mallets (1:4 ratio), FM bells, vibraphone
  (partials 1, 4, 10 with tremolo), kalimba, triangle pads, sine bass, soft electronic
  percussion.

**Failed: imitating acoustic recordings.** The first attempt was lofi hip-hop (fake Rhodes,
fake jazz drums, vinyl crackle). The verdict was "it just doesn't sound right." Lofi's sound
comes from recorded instruments, and synthesis can't fake that convincingly. Don't attempt
piano, strings or orchestra, acoustic guitar, brass, vocals or realistic drum kits. If a
brief needs them, say so and propose licensed samples instead.

## Checks that stand in for listening

Run all of these and report the numbers to the person you work for. Then ask them to listen;
their ears are the real test.

- **Seam check:** printed by the script; should be about 1e-13.
- **`finalize.py`:** frames match, -18.0 LUFS, peak at or below -1 dBTP.
- **Band balance** against this game's reference tracks (`finalize.py --compare`). Tracks in
  the same game should be within about 2 dB of each other in every band. Reference values (dB
  relative to the whole track):

  | Band (Hz) | Neon Grid (NeCity) | Skyline Rising (NeCity) | Golden Hour (Alpha++) | Golden Hour Warm (vibe) |
  |---|---|---|---|---|
  | 20–60 | -3.6 | -4.4 | -15.8 | -16.0 |
  | 60–250 | -4.4 | -3.5 | -3.3 | -2.4 |
  | 250–1k | -7.7 | -8.3 | -3.6 | -4.2 |
  | 1k–4k | -15.3 | -14.6 | -11.8 | -17.1 |
  | 4k–8k | -24.0 | -24.0 | -23.4 | -38.2 |
  | 8k–20k | -24.6 | -23.4 | -36.3 | -43.9 |

  Warning signs: 1k–4k below about -20 sounds muffled, which is what the failed lofi had at
  -24. A 20–60 band louder than 60–250 sounds boomy. Energy below 30 Hz is wasted; a bass
  layer an octave below a low root put content at 22 Hz, so keep it out.
- **Per-section RMS** (each 4 or 8 bars) to confirm the arrangement builds. **L/R
  correlation** around 0.7–0.8 means healthy stereo width.

## Lessons from feedback

- **Tempo:** for NeCity, 100 BPM was preferred over a calmer 84 BPM version ("sounded better
  at the higher BPM"). Keep energy through tempo, and calm things down with arrangement and tone.
- **"A little warmer"** meant a small step: about -3 dB at 1–4 kHz and +1 dB in the low mids.
  The first try cut 1–4 kHz by 7 dB, which risks the muffled lofi sound. Measure against the
  original and move in small steps.
- **When feedback on a sound is lukewarm or vague** ("the bells were just OK"), don't guess
  at one replacement. Render **level-matched A/B/C options** of the same passage (see
  `MELODY=` in `alphapp/scripts/golden_hour_warm.py`), then full loops of each. Since they
  share a backing track, all of them can ship as in-game variations.
- **Make variations by changing data, not code:** same instruments, new key, progression,
  melody, arpeggio pattern and seed. That keeps a game's tracks sounding like one soundtrack.

## Making a new track (checklist)

1. Read the game's style guide (`necity/README.md` or `alphapp/README.md`).
2. Copy the closest script to `<game>/scripts/<new_name>.py`. Change the docstring title, the
   **seed**, and the output filename.
3. Change the key/chords (`CH`, `PROG`), the melody phrases, the arpeggio or mallet pattern,
   and the arrangement. Keep the instrument palette unless the brief asks otherwise.
   Use `mtof`: MIDI 69 = A4 = 440 Hz, 60 = middle C.
4. Render, confirm the seam check, then `finalize.py` into `<game>/tracks/<new_name>.ogg`.
5. Compare against the game's other tracks with `--compare`, and fix balance outliers in the mix.
6. Add the track to `tools/build_all.sh` and to the catalog in `README.md` and the game's README.
7. Commit the script and the OGG (not WAVs or `build/`).

## Engine integration notes

- Loop the entire file; the loop point is the file boundary. Don't fade, trim or pad it.
- OGG Vorbis decodes easily in a custom engine (for example with the public-domain stb_vorbis).
- Tracks that share key and chords (Neon Grid and Neon Grid Calm; the Golden Hour Warm
  variants) can crossfade. Use a slow fade of a few seconds when tempos differ.
- Scripts already render each part as a separate stem (`pad`, `bas`, `drm`, ...). Exporting
  those stems for adaptive music (adding layers as the city grows) is a planned extension.
